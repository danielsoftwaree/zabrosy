# Маркер: правила работы агентов

Начните с [README.md](README.md) и [текущей архитектуры](docs/architecture.md). Работу ведите по [спецификациям](docs/specs/) и отмечайте фактический результат в [задачах](docs/tasks/). Старые `marker-react-*.md` — исторический материал. `marker-mobile.html` выбран пользователем как визуальный и сценарный образец этой версии; его решения об отдельной Vite SPA, отсутствии backend и старой модели данных заменены текущими документами.

## Код

- Это один проект React + TypeScript strict на TanStack Start. Предметные части: `survey`, `journal`, `map`, `account`; маршруты собирают экраны, логика живёт в модулях.
- `shared` не импортирует модули. Импортируйте соседний модуль через его публичный интерфейс. Не создавайте пустые слои и абстракции для гипотетических реализаций.
- Чистые расчёты держите отдельно от React, IndexedDB, Supabase и DOM. `tooling/` — место для конфигураций, когда их размещение поддерживает инструмент.
- Не используйте `useEffect` для производных значений и действий пользователя. Эффект нужен для связи с внешней системой: подписка, датчик, Canvas и подобное. Очищайте подписки и ресурсы. Не добавляйте мемоизацию без конкретной причины.
- Сначала проверьте платформенный API или уже установленный хук. Навык Reactuse не требует установки всей библиотеки и не оправдывает лишнюю зависимость.
- Секунды падения не превращаются в глубину; выбранная длина лески не равна горизонтальной дистанции; неизвестное измерение не превращается в ноль. Сохраняйте происхождение оценки и снимок калибровки заброса.
- Приложение должно запускаться и вести локальный промер без входа, сети, датчиков и Supabase env. Разрешения запрашиваются только по действию пользователя.

## Интерфейс

У проекта пока **нет утверждённой дизайн-системы**. Визуальный и интерактивный ориентир этой версии — `marker-mobile.html`: сохраняйте его композицию, карточки, нижнюю панель и характер действий, адаптируя их к достоверной модели данных и доступности. Не выдавайте образец за окончательный бренд. Текущие ограничения описаны в [дизайне](docs/design.md).

## Проверка и документация

На изменение поведения пишите небольшой тест на наблюдаемом уровне: расчёт, переход промера, сохранение или пользовательский путь. Не тестируйте конфигурацию и простую обвязку ради числа тестов. Перед завершением запускайте доступные `typecheck`, `lint`, `test`, `build`; для PWA и storage проверяйте собранное приложение через origin. Физическую проверку iOS и датчиков обозначайте отдельно от эмуляции.

Новые решения фиксируйте кратко в `docs/decisions/`, если они меняют интерфейсы модулей, модель данных или эксплуатацию. Не записывайте планы как уже сделанные функции. Навыки и их pinned-источники указаны в [skills.md](docs/skills.md). Инструкции навыка уступают явным требованиям пользователя и этому файлу.
