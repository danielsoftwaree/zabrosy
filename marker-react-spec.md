# Маркер · React
## Спецификация мобильного приложения для промера с берега

**Версия:** 1.0 · **Дата:** 26.09.2026 · **Статус:** спецификация к реализации, не описание уже готовой React-версии.

**Базовый прототип:** `reference/marker-mobile.html`. Исходники той же версии находятся в `reference/legacy-source/src/`. Текст встроенных `core.js`, `maps.js` и `app.js` совпадает с исходниками из приложенного архива после удаления внешних пробелов. SHA-256 HTML: `15bfb5d63384c44359005e623eed5c84e30a5a29e1e91ea6ff43d61e00e1b0a7`.

**Главное решение:** перенести продукт на React + TypeScript, сохранив сектор главным экраном, а измерения — отдельной проверяемой логикой. Это не перенос монолитного HTML в один React-компонент и не новая настольная панель.

В документе «должно» означает критерий приёмки. Численные UX- и performance-бюджеты ниже — целевые требования, а не результаты измерения текущего HTML. Проверенная база, предлагаемые изменения и отложенные функции разделены.

## 1. Задача продукта

Рыболов приходит на берег, выбирает ориентир, забрасывает маркерный груз и записывает ощущения при протяжке к себе. Приложение помогает восстановить, **на каком направлении и примерно на какой длине лески произошло наблюдение**, повторить заброс и выбрать участок для проверки кормушкой.

Основная последовательность:

> Выбрал направление → коснулся воды → почувствовал дно → посчитал обороты → отметил ощущение → закончил подмотку → получил след наблюдений.

У пользователя заняты руки, взгляд направлен преимущественно на воду и удилище. Телефон должен требовать коротких касаний, а не заполнения формы. Ни регистрация, ни интернет, ни разрешение на датчики не являются условием первого промера.

### Что именно строится

**React web application / PWA**, ориентированное на портретный телефон. Это не React Native. Базовые данные хранятся на устройстве. Сервер, аккаунты и облачная синхронизация в первый релиз не входят.

Рабочее название — «Маркер». «Цыгылинка» — название исходной сессии, а не ограничение приложения одним водоёмом. Настройки карты могут начинаться с района исходного прототипа, но этот центр нельзя выдавать за определённую GPS позицию пользователя.

### Неподвижные границы достоверности

| Данные | Допустимая интерпретация | Недопустимая интерпретация |
|---|---|---|
| Обороты ручки × выборка катушки | Приблизительная выбранная длина лески | Точное расстояние по горизонтали или по дну |
| Время от воды до дна | Результат ручного замера для сравнения | Глубина в метрах по универсальному коэффициенту |
| «Стук», «вязко», «подъём» | Ощущение пользователя | Автоматически установленный грунт или измеренная высота свала |
| Луч на снимке | Приблизительная привязка направления и длины | Измеренная подводная траектория груза |
| Введённая глубина | Значение с явно указанным происхождением | Основание автоматически достроить дно всего сектора |
| Проверка кормушкой | Зафиксированный результат проверки участка | Гарантия наличия рыбы или сохранения условий |

Эти ограничения должны отражаться в модели данных, а не только в справке.

## 2. Что уже есть в HTML и что меняется

Аудит выполнен по предоставленным файлам, не по прежним сообщениям в чате. В архиве есть тесты и отчёты. Их браузерные сценарии использовали мобильную эмуляцию, имитацию Storage API и датчиков; они **не подтверждают полевую работу GPS, компаса, живого WMS и офлайн-перезапуска PWA**.

| Область | В базовом HTML | Цель React r1 |
|---|---|---|
| Главный экран | Canvas, сектор, нижняя панель | Та же карта во весь экран; компактные React-слои управления |
| Промер | `armed / falling / retrieve / interrupted` | Явная конечная машина состояний, включая подтверждение сохранения |
| Дистанция | Оценка или полная подмотка × выборка | Сохранить формулы, разделить длину лески и измерение по карте |
| Отметки | Шесть ощущений и число оборотов | Сохранить; добавить явное происхождение и состояние «позиция неизвестна» |
| Кандидат | Статус всего заброса | Отдельная цель: конец заброса, конкретная отметка или интервал |
| Геопривязка | Координаты в каждом забросе | Станции и неизменяемые версии привязки; снимок в забросе |
| Повтор заброса | Копирует старый относительный угол с предупреждением | Проверяет станцию; при смене нуля пересчитывает угол по сохранённому азимуту |
| Снимок | Собственный WMS-рендерер в `FieldMap` | Провайдер изображений за адаптером; MapLibre загружается отдельно |
| 3D | Canvas-проекция наблюдений | Сохранить смысл и лёгкий рендер; не добавлять вымышленную поверхность |
| Хранилище | Синхронный LocalStorage, архив до 20 сессий | IndexedDB, атомарные операции, резервные копии, защита от конфликтов |
| Импорт/экспорт | v1/v2, HTML, JSON, CSV, PNG | Импорт v1/v2/v3; те же форматы экспорта с уточнёнными гарантиями |
| Демо | Изолировано от реальной сессии | Сохранить отдельный контекст и маркировку |
| PWA | Простой Service Worker | Версионный кэш, обновление только после подтверждения вне промера |
| Справка | Отдельная страница | Сохранить отдельно от полевого ввода |

Перенос считается завершённым по проверяемому поведению, а не по внешнему сходству.

## 3. Объём первого релиза

**R1 должен включать:** сектор и быстрый промер; калибровку катушки; журнал и исправления; кандидатов и проверку кормушкой; необязательные снимок, GPS и ориентацию; схему 3D-наблюдений; справку; локальное сохранение; импорт старых данных; JSON/CSV/PNG и переносимый HTML; установочную PWA-оболочку.

Реализация идёт этапами. Сначала обязателен полностью рабочий автономный сценарий; карта и датчики не должны задерживать проверку основной логики. Промежуточный core-build не называется завершённым R1, пока не реализована остальная согласованная совместимость.

**За рамками R1:** распознавание оборотов телефоном, голосовой ввод, фоновая запись при заблокированном экране, автоматическое определение глубины, батиметрическая интерполяция, прогноз клёва, общая карта чужих точек, аккаунты, синхронизация, платные подписки, офлайн-загрузка района снимков, нативные приложения.

Эти функции не добавляются «заодно». Для них нужны отдельные данные, решения о приватности и проверки.

## 4. Мобильная компоновка и навигация

### 4.1. Главный экран

```text
┌─────────────────────────────────┐
│ Маркер · сессия             ☰    │  компактный верхний слой
│ [ Сектор | Снимок | 3D ]        │
│                                 │
│             карта               │  основное содержимое
│         лучи и отметки           │
│          выбранный луч          │
│                         компас  │
│                                 │
├──────── контекстный dock ────────┤
│ ≈ 30 м               ← 15°      │  готовность
│          Начать промер          │
└─────────────────────────────────┘
```

Это схема иерархии, не обязательные пиксельные размеры. Карта находится фоном на весь viewport. Верхняя панель, переключатель и нижняя панель — независимые слои. Обычной прокручиваемой страницы с картой между блоками текста здесь нет.

Основные требования:

- Портретные размеры проверки: 320×568, 360×640, 390×844, 430×932 CSS px. На широком экране — тот же мобильный интерфейс по центру, максимум 520 px, без desktop-dashboard.
- Использовать динамическую высоту viewport и safe-area. Панель не закрывает нижний системный жест. Экранная клавиатура не прячет подтверждение ввода.
- В состоянии готовности на экранах высотой от 640 px целиться минимум в 60% свободной видимой карты; при протяжке — минимум в 45%. Для 320×568 важнее не уменьшать touch-target: допускается компактный режим с минимум 160 px полезной высоты сектора.
- Минимальная цель обычного касания — 48×48 CSS px; на 320 px допустимо 44×44. Главная кнопка — не ниже 56 px. Между соседними действиями — минимум 8 px.
- Один доминирующий призыв к действию в каждом состоянии. Настройки и пояснения раскрываются отдельно.
- Наклон в landscape не уничтожает черновик и не блокирует приложение. Компас может попросить вернуться в поддерживаемую позу; ручной ввод остаётся доступным.

### 4.2. Маршруты

Для статического размещения принять hash routing. Это проектное решение: оно не требует настройки серверных rewrite для вложенных страниц.

| Маршрут | Назначение |
|---|---|
| `/#/field` | Карта и текущий промер |
| `/#/journal` | Забросы активной сессии |
| `/#/casts/:castId` | Карточка, лента отметок, исправления и цели |
| `/#/guide` | Инструкция и учебный разрез |
| `/#/settings` | Катушки, датчики, поведение приложения |
| `/#/data` | Экспорт, импорт, сессии, резервные копии |

Меню — отдельный sheet. Настройка угла, длины, оборотов, калибровка и финальное подтверждение — небольшие sheets поверх карты. Кнопка Back сначала закрывает sheet, затем возвращает из маршрута. Она не отменяет промер без подтверждения.

### 4.3. Визуальный язык

Сохранить узнаваемые цвета текущего HTML: тёмно-зелёные действия, светлая поверхность, спокойный фон воды, салатовый акцент. Вынести CSS-переменные в tokens. Шесть ощущений различаются **текстом и символом**, а не только цветом.

Стандартный шрифт системы, числа таймера с одинаковой шириной символов. Основной текст не меньше 16 px; мелкие подписи не должны нести единственный способ понять критическое состояние. Постоянные предупреждения о несохранённых данных нельзя заменять исчезающим toast.

## 5. Полный пользовательский сценарий

### 5.1. Первый запуск

Сразу открыть сектор. Не показывать обязательную карусель обучения, форму сессии или запрос GPS. Название и текущий комплект можно изменить позже.

До калибровки виден компактный статус «Катушка: ≈ 80 см/об. · оценка» — наследуемая стартовая оценка, **не измеренная характеристика катушки**. Он не запрещает работу. Начальная дистанция 30 м допустима только как явно помеченное предположение, до выбора пользователем.

Первый вход в справку и демо — через меню. Первый вход в снимок предлагает два действия: подтвердить своё место и ориентир. На сам сектор это не влияет.

### 5.2. Калибровка катушки

Пользователь вводит отмеренную длину и число **оборотов ручки**, либо вводит сантиметры за оборот напрямую. Поддерживаются десятичная запятая и дробные обороты.

`pickupMetersPerHandleTurn = knownLengthMeters / countedHandleTurns`

Источники различаются: самостоятельный замер, паспорт катушки, ручная оценка, старые данные. Только ввод двух фактически измеренных величин либо явное подтверждение самостоятельного измерения может установить метод `measured`. Прямая замена поля не наследует незаметно старую отметку «измерено».

Каждый начатый заброс получает снимок калибровки и снасти. Изменение настроек влияет на следующие забросы. Пересчёт истории возможен только отдельной осознанной операцией, не входит в обычную смену настройки.

### 5.3. Выбор направления

В секторе касание свободного места задаёт направление и приблизительную дистанцию. Drag одного пальца изменяет выбранный луч; pinch — масштаб. Касание существующего заброса открывает его, а не перемещает прицел.

Угол 0° связан с выбранным ориентиром; отрицательные углы — влево, положительные — вправо. Короткое обозначение угла: `← 15°`, `0°`, `→ 20°`.

Можно изменить угол числом или навести телефон по датчику. Жесты и показания датчика обновляют **предпросмотр**; после «Начать промер» направление, привязка, выборка и снасть фиксируются в черновике. Поворот телефона во время подмотки их не меняет.

### 5.4. Таймер «вода → дно»

После «Начать промер» нижнюю большую область занимает кнопка «Коснулся воды». При первом касании запускается секундомер, при следующем отдельном касании области «Дно» фиксируется результат.

Область захвата занимает не меньше 40% высоты телефона, когда идёт замер. Карта может оставаться видимой, но не принимает случайные изменения прицела. Отмена и пропуск — отдельные подписанные кнопки, не невидимые жесты.

**Алгоритм ввода:** запомнить `performance.now()` на `pointerdown`, подтвердить действие только валидным завершением того же жеста. `pointercancel` отменяет жест. Повторное событие `click` не запускает второе действие. Следующее состояние не должно получить «призрачный» клик из прошлого. Время относится к началу валидного касания, а не задержке перерисовки. Keyboard/assistive activation имеет отдельный безопасный путь.

Не использовать произвольный запрет всех вторых касаний на 250–500 мс как замену обработке жестов: он может отбросить реальное короткое падение. От одного физического жеста принимается максимум одно действие.

Отображать десятые секунды. Хранить измерение с достаточной для ручного таймера точностью, например сотые; это не заявление о физической точности измерения. Не пересчитывать результат в метры.

При скрытии страницы, reload или достижении лимита 600 с замер становится `interrupted`, время не считается достоверным. Обороты и уже существующие отметки сохраняются. Пользователь может повторить падение или продолжить без времени.

### 5.5. Протяжка и быстрые отметки

После фиксации дна показать:

```text
[ 15 оборотов · изменить ]  [ +1 ] [ +5 ]
[ Ровно ] [ Стук ] [ Вязко ]
[ Подъём ] [ Трава ] [ Упор ]
Последняя отметка · ≈ … м             ↶
                 Закончить
```

`+1` и `+5` изменяют накопленный счётчик. Пользователь вправе считать мысленно и вводить число блоком; приложение не требует касания после каждого оборота. Нажатие ощущения добавляет **одну** отметку с текущим накопленным числом. Модальное окно и обязательная заметка не открываются.

Удержание счётчика допустимо как настройка, выключенная по умолчанию ради защиты от случайного прижатия. При включении: первоначальное увеличение один раз, задержка до повторов, остановка на `pointerup`, `pointercancel`, потере capture и скрытии страницы. Один непрерывный hold — одна группа отмены.

Одинаковые числа оборотов у двух отметок допустимы: это два наблюдения в одном приблизительном месте. Новое ощущение не должно автоматически заменять старое. Undo удаляет последнюю операцию или группу удержания; оно не может оставить отметку с числом оборотов больше текущего счётчика.

Ручная корректировка счётчика не сдвигает историю скрыто. Для исправления ошибочной отметки есть её карточка. Уменьшение текущего числа ниже уже записанной отметки требует сначала исправить отметку либо отменить связанную операцию.

### 5.6. Завершение

«Закончить» открывает краткое подтверждение: итоговые обороты, вариант полной/неполной подмотки и рассчитанная дистанция. Заметка, глубина и кандидат скрыты в дополнительных полях; вводить их не обязательно.

Пересчёт по оборотам разрешён только после осознанного подтверждения **«Вся подмотка посчитана»**: леска выбрана и учтён весь путь, не только последние несколько метров. Значение не предвыбрано. При неполной или неполностью посчитанной подмотке сохранить исходную оценку, а не объявлять текущий счёт полной дистанцией.

После подтверждённой записи в хранилище — назад в готовность, с прежним направлением и уточнённой дистанцией. Короткое сообщение «Заброс сохранён» и действие «Открыть». Повторное нажатие сохранения не создаёт дубль.

### 5.7. Кандидат находится не обязательно в точке падения

Ключевое дополнение к HTML: выбранная площадка может быть между берегом и концом заброса. Карточка позволяет выбрать конкретную отметку или интервал между двумя отметками как `FishingTarget`.

Действие «Проверить кормушкой» относится именно к этой цели. Записываются два независимых результата: держится ли кормушка, выматывается ли без постоянных зацепов. Только оба положительных результата дают статус «Проверено кормушкой».

При изменении расположения цели проверка остаётся исторической записью, но текущий статус возвращается в «Кандидат». Старый `working` из v2 без точного участка импортируется как проверка заброса с неуточнённой позицией; приложение не придумывает место проверки.

## 6. Машина состояний промера

Использовать типизированный reducer и команды. Не создавать набор независимых boolean-флагов `isStarted / isFalling / isFinished`. В R1 отдельная библиотека state machine не обязательна.

| Состояние | Допустимые главные действия | Переход |
|---|---|---|
| `idle` | Выбор направления, старт | `armed` |
| `armed` | Вода, пропустить, отменить | `falling`, `retrieving`, `idle` |
| `falling` | Дно, без времени, прерывание | `retrieving` или `interrupted` |
| `interrupted` | Повторить падение, без времени, отменить | `armed`, `retrieving`, `idle` |
| `retrieving` | Обороты, отметки, undo, закончить | `retrieving` или `review` |
| `review` | Подтвердить итог, вернуться | После записи — `idle`, иначе `retrieving` |

Сохранение (`saving / saved / error / conflict`) — отдельное состояние дискового ввода, а не новая физическая стадия промера. Пока идёт commit, нельзя повторить commit. Ошибка записи оставляет черновик и позволяет повторить запись или экспортировать его.

При повторном открытии `falling` восстанавливается только как `interrupted`. Значение `performance.now()` не сохраняется для использования после reload. `armed`, `retrieving` и `review` восстанавливают данные и безопасную соответствующую стадию.

Запрещено начинать второй черновик, заменять сессию импортом, сменять станцию или включать демо, не решив судьбу текущего черновика. Открытие справки при падении сначала прерывает таймер; при протяжке ничего не удаляет.

## 7. Измерения и производные координаты

### 7.1. Основные формулы

Пусть `q` — метров за оборот ручки, `N` — вся подтверждённая подмотка, `nᵢ` — счётчик при отметке.

```text
L₀ ≈ N × q
Lᵢ ≈ (N − nᵢ) × q
```

Пример-эталон: `q = 0,8`, `N = 50`, `nᵢ = 10` → исходная длина ≈40 м, отметка ≈32 м. Это обязательный unit test.

Для частичного промера с исходной оценкой длины лески `Lguess` можно вычислять предварительное `Lᵢ ≈ Lguess − nᵢ × q`, но подписывать его как оценку. После полной подтверждённой подмотки все точки выводятся из сохранённых оборотов и снимка `q`, а не из накопленных округлений.

**Противоречие не скрывается:** если предварительное значение отрицательно, не складывать все дальнейшие отметки в ноль на берегу. Сохранить обороты, вернуть позицию `unknown`, показать «Исходная дистанция мала — уточнится после полной подмотки».

### 7.2. Три разных вида расстояния

`line_retrieval` — оценка длины лески по полной подмотке. `estimated_line` — пользовательская/стартовая оценка длины. `map_ground` — расстояние между выбранными точками снимка. Импортированная дистанция неясного происхождения имеет `legacy_unspecified`.

Эти значения нельзя молча смешивать. Внизу карты компактно показывать источник: «≈ 40 м · по оборотам», «≈ 30 м · оценка», «≈ 35 м · по снимку». Из расстояния по снимку нельзя безоговорочно вычитать обороты и называть результат оставшейся леской.

Если есть только `map_ground`, до полной подмотки на карте видны конец луча и упорядоченная лента наблюдений без утверждения их метрических положений. Полная подмотка позволяет добавить позиции по леске; исходный выбор по карте остаётся в данных.

### 7.3. Геометрия сектора

Локальный 0° направлен на ориентир. Для схематического расстояния `d`:

```text
x = sin(angle) × d
y = cos(angle) × d
```

Это раскладка наблюдений, не восстановленная форма натянутой лески. Течение и дуга лески не моделируются. Луч изображается пунктиром и не называется GPS-треком груза.

Единицы модели — метры, секунды, градусы и обороты ручки. Округление — только на отображении. Ввод принимает запятую и точку. `NaN`, `Infinity`, отрицательные обороты и некорректные координаты запрещены.

### 7.4. Единые диапазоны

Для обычного ввода R1: дистанция >0 и ≤500 м; выборка 0,05–3 м/об.; счётчик 0–10 000; груз 1–500 г; глубина 0–100 м либо неизвестна. Это технические границы интерфейса, не рекомендации по снастям.

Не наследовать конфликт HTML: часть интерфейса ограничена 180 м, а записи допускают 500 м. Сектор должен иметь auto-fit для поддерживаемых дистанций, например диапазон отображения до 600 м с полем вокруг края. Направление в данных нормализуется до `[-180, 180)`; стандартный видимый сектор может оставаться ±85°. Внеэкранные старые данные не обрезаются: счётчик «N вне сектора», журнал и команда выбора подходящей привязки.

При импорте выход за поддерживаемый диапазон показывается в отчёте; исходник сохраняется. Молчаливый clamp повреждённых значений запрещён.

## 8. Станции, ориентиры и повтор заброса

`Station` — физическое место пользователя на берегу. `SurveyFrame` — неизменяемая версия его координат и нулевого ориентира. `CastSetupSnapshot` сохраняет эту версию в момент старта.

Изменение ориентира на той же станции создаёт новый frame. Реальный переход на другой берег создаёт новую station. Исправление координат — явная операция; не допускается незаметно перемещать все старые точки при очередном GPS-обновлении.

Относительный сектор по умолчанию показывает забросы активной станции и совместимой привязки. Географическая карта может показывать несколько станций с разными маркерами. Совпадение координат до последнего знака, как в старом `sectorCasts`, не использовать как идентификатор станции.

**Повторить:** на той же станции и с тем же frame копируются направление и исходная дистанция, но не время и не отметки. При новом нуле и известном истинном азимуте пересчитать `relativeAngle = normalizeDelta(castAzimuth − newReferenceAzimuth)`. При другой станции или неизвестном азимуте не обещать повтор: предложить вручную подтвердить направление либо вернуться к исходной станции.

Создание связей для старых непривязанных записей — только после подтверждения пользователя, что берег и ориентир действительно совпадали.

## 9. Снимок и геолокация

### 9.1. Источник

Базовый провайдер для Польши — ортофото GUGiK / Geoportal. Официальная документация перечисляет WMS/WMTS и сервис высокого разрешения [S2]. Использование растрового WMS-слоя в MapLibre показано в его документации [S3]. Это подтверждает техническую возможность интеграции, но не доступность конкретного слоя из целевого домена приложения.

В интерфейсе писать **«Снимок» / «Ортофото»**, а не «живой спутник». Атрибуция провайдера всегда видна, не перекрыта нижней панелью. Дату съёмки показывать только при получении реальных метаданных; иначе «Дата снимка неизвестна» в информации о слое.

```text
https://mapy.geoportal.gov.pl/wss/service/PZGIK/ORTO/WMS/HighResolution
https://mapy.geoportal.gov.pl/wss/service/PZGIK/ORTO/WMS/StandardResolution
```

Перед реализацией адаптера проверить `GetCapabilities`: слой, поддерживаемую CRS, версию WMS, порядок координат BBOX, формат изображения и допустимые запросы. Прототип использует Web Mercator; конкретный WMS-контракт не копировать вслепую.

Проверить CORS именно для WebGL-загрузки: картинка, которую можно показать обычным `<img>`, не обязательно доступна в качестве текстуры MapLibre. При недоступности CORS не создавать бесконтрольный proxy и не обходить ограничения сервиса. Фиксировать техническое решение отдельно; сектор работает независимо.

### 9.2. Взаимодействие

В снимке один палец перемещает карту, pinch меняет масштаб. Случайный tap при завершении pan не выбирает заброс. Для установки берега и ориентира используется центральный прицел с явными кнопками подтверждения.

GPS запрашивается только после «Найти меня». Отображаются точка и указанная API погрешность, когда она доступна. Пользователь подтверждает либо исправляет берег. GPS не считается точным измерением позиции удилища.

После выбора берега пользователь выбирает видимый ориентир. Слишком близкий ориентир (менее 5 м) отклоняется как непригодный для данного UI; короткая база или грубая GPS-позиция сопровождаются предупреждением, а не придуманной точностью угла.

### 9.3. Отказы и приватность

Состояния провайдера: `idle`, `loading`, `ready`, `unavailable`, `offline`. При ошибке high-resolution разрешён один переход на стандартный слой; после отказа обоих — сообщение и кнопка повторить. Бесконечный spinner и цикл повторных запросов запрещены.

Запросы снимков раскрывают провайдеру район просмотра и обычные сетевые метаданные. Собственный сбор геолокации, аналитика и отправка записей на сервер в R1 отсутствуют. Учебные точки никогда не выдаются за карту реального дна.

## 10. Компас, ориентация и удержание экрана

Ориентация — дополнительный способ выбрать угол, не обязательная измерительная функция. API зависит от безопасного контекста и разрешений; абсолютная и относительная ориентации различаются [S4].

Рабочий сценарий: пользователь включает датчик отдельной кнопкой, держит телефон в поддерживаемой позе, направляет верх на ориентир и нажимает «Это 0°». Затем поворачивает телефон к направлению заброса. Относительный угол вычисляется относительно этой калибровки.

Нельзя маркировать `360 − alpha` как истинный север без проверки источника и положения устройства. Сохранять происхождение показаний: относительное, магнитное, истинное или неизвестное. Для геопривязки предпочитать истинный азимут, полученный из двух точек карты плюс откалиброванный относительный угол.

Сглаживать угол циклически: переход 359°→1° не должен давать 180°. Для R1 поддерживать одну документированную позу телефона, например почти горизонтально в портретной ориентации; вне неё блокировать применение сенсорного угла и предлагать ручной режим. Не показывать уверенное направление при неподдерживаемом наклоне.

Если нет свежих показаний больше 2 с, угол помечается устаревшим и не применяется автоматически. После 6 с без показаний предложить ручной способ. При смене станции, нуля или ориентации экрана нужна повторная калибровка. Показания фиксируются при старте заброса.

Подписки и разрешения организовать через `OrientationAdapter`. Завершение функции отключает слушатели. Отказ не повторяет запрос бесконечно и не блокирует сектор.

Wake Lock запрашивается только на время активного промера при включённой настройке. API работает с видимым документом и может быть освобождён браузером [S5]. На `release` обновить индикатор; после возврата страницы попытаться получить заново. Завершение и отмена освобождают блокировку. Отсутствие Wake Lock не считается ошибкой приложения.

Вибрация — необязательное улучшение, всегда с визуальным подтверждением. Никакой сценарий не должен зависеть от её наличия.

## 11. Лента наблюдений, профиль и 3D

Главный инструмент анализа одного заброса — лента от дальнего участка к берегу с ощущениями и приблизительными позициями. Рядом указывать источник дистанции. По касанию открывается отметка с возможностью исправить число оборотов и добавить отдельно измеренную глубину.

**3D в R1 — схема наблюдений.** Сохранить текущий лёгкий подход Canvas, не подключать Three.js только ради наклона плоскости. Режим открывается отдельно; orbit одним пальцем, масштаб двумя. Переключение вида не меняет данные.

При отсутствии глубины рисовать полый знак на явно условной плоскости с подписью «Глубина неизвестна». Его вертикальная координата относится только к раскладке интерфейса; значение `depth=0` в модель не записывается. Измеренная глубина рисуется отдельным знаком и вертикальным отрезком.

Не соединять точки поверхностью и не присваивать высоту отметке «Подъём». Если нет сопоставимых измеренных глубин, не показывать числовой профиль как реальное дно. Данные разных станций, дат и неизвестных вертикальных отсчётов не объединяются в общую измеренную поверхность.

Глубины, импортированные из старого числового поля без метода измерения, сохраняются как `legacy_unverified` и помечаются соответственно, а не получают статус проверенного замера.

## 12. Архитектура React

### 12.1. Принятый стек

Это выбор для данного приложения, не утверждение, что React требует именно такую архитектуру. Официальное руководство допускает сборку приложения с Vite и шаблоном React/TypeScript [S1].

| Слой | Решение |
|---|---|
| UI | React + TypeScript, strict mode |
| Сборка | Vite, SPA, статический HTTPS-хостинг |
| Навигация | React Router в hash-режиме |
| Состояние | Типизированный reducer доменных команд + небольшой Zustand store для активной сессии/UI |
| Валидация | Zod на границе импорта/хранилища/форм; не на каждом кадре |
| Сохранение | IndexedDB через Dexie |
| Сектор и 3D-схема | Собственный Canvas 2D renderer без React-узла на каждую отметку |
| Снимок | Lazy-loaded MapLibre + WMS provider adapter |
| PWA | vite-plugin-pwa / Workbox, обновление по подтверждению |
| Тесты | Vitest, React Testing Library, Playwright, физические телефоны |
| Стили | CSS Modules / обычный CSS с tokens; без обязательной тяжёлой UI-библиотеки |

Не фиксировать номера пакетов по памяти. При старте реализации выбрать совместимые стабильные версии, записать их в lockfile и CI. Не нужны SSR, Next.js, Redux, TanStack Query или backend исключительно ради переноса этого прототипа.

### 12.2. Границы модулей

```text
src/

  domain/
    model/             # типы v3 и invariants
    survey/            # reducer, команды, undo, finalize

  features/
    field/             # FieldScreen, HUD, dock, mode switch
    survey/            # timer pad, counter, feeling palette, finish sheet
    calibration/       # катушки и калибровка
    stations/          # берег, ориентир, версии привязки
    journal/           # список, карточка, цели и feeder check
    data/              # экспорт/импорт, архив, recovery
    guide/             # справка и отдельный demo-context
  rendering/
    sector/            # imperative Canvas renderer + hit testing
    observations3d/    # проекция наблюдений
    imagery/           # MapLibre lifecycle и провайдер
  platform/
    orientation/       # permissions и device readings
    geolocation/
    wake-lock/
    persistence/       # Dexie, repositories, serialized writes
    lifecycle/         # visibility, cross-tab conflicts, update guard
  migrations/          # v1 -> v3, v2 -> v3, legacy validation
  exports/             # JSON, CSV, PNG, portable HTML
  shared/ui/           # Button, BottomSheet, InlineStatus, NumberInput
  styles/              # tokens и мобильная оболочка
```

### 12.3. React не рисует каждый кадр

React управляет жизненным циклом и DOM-контролами. Canvas renderer принимает render snapshot и самостоятельно выполняет `requestAnimationFrame` по invalidation. Координаты drag, live-компас, `performance.now()` и камера не должны вызывать перерендер всего дерева на каждом событии.

Важные действия проходят через команды: `ADD_TURNS`, `ADD_MARK`, `SAVE`, `CHANGE_FRAME`. После команды обновляется доменное состояние, отдельно запускается запись. Императивный рендер не имеет права произвольно менять базу или доменную модель.

Разделить три состояния: долговечные доменные записи; краткоживущий UI; высокочастотный runtime рендера и датчиков. IndexedDB — источник сохранённых данных; активный store — рабочая проекция. Не поддерживать две независимо изменяемые «истины» между Zustand и Dexie.

`useEffect` должен уметь повторный mount/unmount: отключать слушатели, отменять RAF, уничтожать MapLibre, освобождать Wake Lock. React Strict Mode не должен создавать двойные подписки и дубли отметок.

## 13. Модель данных и инварианты

Полные стартовые TypeScript-контракты находятся в `contracts/domain.ts`. Это контракты для реализации, не готовая библиотека.

| Сущность | Назначение |
|---|---|
| `Session` | Рыбалка, архивность, активная станция, real/demo |
| `Station` | Место на берегу с устойчивым ID |
| `SurveyFrame` | Версия координат и нулевого ориентира |
| `ReelProfile`, `ReelCalibration` | Катушка, выборка и происхождение калибровки |
| `CastSetupSnapshot` | Зафиксированные параметры конкретного заброса |
| `CastDraft`, `Cast` | Незавершённый / завершённый промер |
| `BottomMark` | Ощущение, накопленные обороты либо импортированная позиция |
| `DepthMeasurement` | Глубина с происхождением, отдельно от времени |
| `FishingTarget`, `FeederCheck` | Выбранный участок и его проверка |
| `LegacyBackup` | Неперезаписанный исходник миграции |

`ExportBundleV3.schemaVersion = 3`. Это версия формата данных, а не версия IndexedDB и не версия React-приложения.

Обязательные инварианты:

1. Все ID уникальны внутри своих наборов; ссылки на session, station, cast и mark существуют.
2. Снимок настройки заброса не зависит от последующего изменения preferences.
3. `feeder_checked` требует обоих положительных чеков и совпадающей geometry revision.
4. `line_retrieval` требует положительного полного счёта, полной подмотки и подтверждения полноты подсчёта.
5. В завершённом промере отметки по счётчику не превышают итоговое число оборотов.
6. Неизвестные глубины и неизвестные метрические позиции — `null`/явный union, не ноль.
7. Demo-данные не записываются в реальные сессии и всегда помечаются в экспорте.
8. Каждый физический ввод и каждый commit идемпотентен относительно своего ID/gesture token.

Не хранить производные координаты как единственный источник истины. Их можно кэшировать с revision, но исходные обороты, q, frame, source и измерения сохраняются.

## 14. Сохранение, восстановление и миграция

### 14.1. IndexedDB

Таблицы: `sessions`, `stations`, `frames`, `reelProfiles`, `calibrations`, `casts`, `drafts`, `targets`, `legacyBackups`, `meta`. Preferences можно хранить отдельно, но не использовать LocalStorage для полного дерева измерений на каждый tap.

Каждая доменная операция немедленно обновляет UI и ставится в последовательную очередь записи. «Сохранено» показывается после успешного завершения транзакции; до этого — `saving`. Нельзя обещать защиту от потери последнего события, пока запись ещё не завершилась.

Сохранение заброса и удаление его черновика — одна транзакция. Импорт — транзакция после полной валидации. Ошибка quota/доступа оставляет данные в памяти с постоянным предупреждением и действующим экспортом.

Не полагаться только на `beforeunload` или `pagehide`: важные команды сохраняются в ходе работы. Текущий черновик восстанавливается с предложением продолжить или удалить. Удаление сохранённой записи допускает отмену; исходный объект до окончательного удаления доступен для восстановления.

IndexedDB не является облачным backup и по умолчанию не даёт абсолютной гарантии хранения. Можно запросить persistent storage после объяснения, но разрешение не гарантировано [S6]. Экспорт остаётся необходимым.

### 14.2. Две вкладки

Редакция промера содержит `revision`. Запись проверяет ожидаемую revision внутри транзакции; конфликт не разрешается правилом «последняя вкладка победила». Второй редактор получает сообщение, текущий несохранённый вариант можно выгрузить или сохранить отдельной сессией. `BroadcastChannel` допустим для уведомлений, но контроль конфликта должен работать на уровне репозитория.

### 14.3. Совместимость

Импорт должен понимать старый v1, текущий v2, новый v3 и HTML-копии с `<script id="embedded-state" type="application/json">`.

Из HTML извлекаются только данные. Не выполнять ни один его script и не вставлять импортированную разметку в живой DOM приложения. Отклонить неподдерживаемую будущую версию; сохранить возможность скачать исходник без исправлений.

На том же origin возможно предложить перенос ключей `marker-mobile-v2:main-v2` и его архива, а также `cegielinka-casting-map-v1:main`. Другой домен, другой браузер и локальный `file://` не дают новой версии автоматического доступа к старому хранилищу: здесь нужен экспорт/импорт.

Импорт имеет защиту от чрезмерного объёма: стартовый лимит 20 MiB для файла и 50 000 отметок на bundle; превышение отклоняется целиком с объяснением, без обрезания записей. Лимиты регулируются только после нагрузочного теста. Не доверять одному TypeScript-типу: обязательны runtime-проверки и проверка ссылочной целостности.

Перед переносом показывать краткий отчёт: сколько сессий/забросов/отметок, сколько предупреждений, куда они добавятся. Импорт по умолчанию создаёт новые сессии, не затирает текущую. Повторный импорт распознаёт уже перенесённый источник и предлагает осознанное дублирование вместо молчаливого удвоения.

### 14.4. Особые случаи v1/v2

Старый v1 может хранить `featureDistance`, но не реальные обороты. Сохранить такую отметку как `legacy_line`, а не синтезировать «измеренные» обороты через 0,8 м/об. Если прежняя миграция уже создала искусственные обороты, использовать доступный `legacySource` для восстановления происхождения.

v2 `pickupCalibrated=true` без исходных калибровочных измерений — историческое подтверждение пользователя, не новый замер. v2 `fall` сохраняется с методом `legacy`; `fallInterrupted` имеет приоритет над потенциально оставшимся числом. v2 `depth` получает `legacy_unverified`.

Не терять неизвестные новому UI поля: заметки, старые catch/ground/feature-поля и прочее остаются в `LegacyBackup`. Перенос не обязан показывать каждое старое поле в новом интерфейсе, но должен сохранить возможность его получить из backup.

## 15. Экспорт, PWA и статическое размещение

### 15.1. Форматы

| Формат | Гарантия R1 |
|---|---|
| JSON | Полный переносимый bundle v3, включая черновик, происхождение и снимки настроек |
| CSV | Строки cast/mark/target; отдельные поля для счёта, источника расстояния и примерных координат |
| PNG | Схема сектора с легендой и пометкой примерности; не снимок с необязательным CORS |
| HTML | Автономная редактируемая копия основного приложения с данными, без внешних assets для полевого сценария |

Для R1 сохранить возможность продолжить работу в HTML-копии: сектор, промер, журнал, калибровка, 3D-наблюдения и повторный экспорт должны работать без внешних JS/CSS. Собрать отдельный portable entry из тех же React-компонентов, с inline-assets и без Service Worker. Не копировать `document.outerHTML` production-SPA: ссылки на chunks сделают такой файл зависимым от хостинга.

Экспорт использует подготовленный версионный single-file шаблон и вставляет в него JSON данных. Шаблон включается в офлайн-кэш, но не исполняется при обычном старте сайта. Не создавать вторую независимую реализацию UI. Онлайн-снимок и датчики в локальном файле могут быть недоступны; основной сценарий работает в памяти с возможностью экспортировать новую копию. Локальное автосохранение подтверждается фактической доступностью хранилища, а не обещается для любого `file://` браузера.

HTML содержит блок данных `embedded-state`, пригодный для обратного импорта. JSON в нём экранируется так, чтобы `</script>` в заметке не закрыл элемент. Примечания выводятся как текст. В CSV нейтрализуются формульные префиксы в строках. Экспорт PNG из Canvas не должен зависеть от загрузки внешних снимков.

### 15.2. Офлайн

Первый запуск сайта требует получения ресурсов. После успешного precache и подтверждения готовности офлайн должны открываться сектор, промер, журнал, справка, 3D-схема, импорт и экспорт. Это проверяется после закрытия и повторного открытия приложения, а не только отключением сети в уже загруженной вкладке.

Кэшировать нужно и локальные lazy chunks справки/экспорта/3D, иначе обещание офлайн будет неполным. Внешние ортофото в R1 не предзагружаются; офлайн-карта показывает отсутствие снимка без потери наблюдений.

### 15.3. Обновление

Применять prompt-for-update, а не автоматический reload. Документация vite-plugin-pwa предусматривает такой режим [S7]. Пока есть активный промер или незавершённая запись — предложенное обновление отложено. После подтверждения сохранения пользователь может обновить приложение; миграции данных выполняются безопасно.

Статический build должен поддерживать корень и настраиваемый base path. Проверить scope Service Worker, пути manifest и assets. Нужен HTTPS. Публикация на конкретную платформу, включая ChatGPT Sites, — отдельная инфраструктурная операция; наличие подготовленной сборки не означает, что она размещена.

## 16. Производительность, жесты и доступность

### 16.1. Целевые бюджеты

| Метрика | Цель и способ проверки |
|---|---|
| Добавление оборота/ощущения | Визуальный отклик p95 ≤100 мс на зафиксированном тестовом телефоне |
| Основной Canvas | Цель 60 fps при drag/pinch; отдельно профиль кадра на 100 забросах / 2 000 отметках |
| Работа без жестов | Нет непрерывного цикла рендера и лишних запросов датчиков |
| Первый JS основного сценария | Бюджет ≤250 KiB gzip без отложенного MapLibre; при превышении — отчёт и решение |
| Отображение числа таймера | До 10 обновлений текста в секунду; расчёт по монотонным часам |
| Сохранение команды | Цель p95 ≤300 мс на тестовом устройстве; статус показывает реальный результат |
| Нагрузочный набор | 1 000 забросов / 20 000 отметок: приложение открывается, импорт и экспорт не теряют данные |

Нагрузочная поддержка не требует рисовать все подписи одновременно. Использовать culling, упрощение неактивных лучей и агрегацию наложенных hit-targets. Все записи остаются доступны в журнале.

MapLibre загружается только при первом открытии снимка. Во время основного сценария не работают одновременно два активных картографических движка. DPR Canvas ограничить разумным значением, например 2, как в прототипе.

### 16.2. Согласование жестов

Pointer Events, capture и `touch-action` применяются локально: карта управляет своими pan/pinch, sheets остаются прокручиваемыми. Спецификация Pointer Events описывает `pointercancel` и управление прямыми жестами через `touch-action` [S8]. Не навешивать глобальный запрет всех жестов на документ.

После pinch отпускание последнего пальца не должно выбирать новую точку. При drag по нижней панели карта не двигается. При переходе режима активный жест завершён или отменён. Зоны карты под sheet не принимают касания.

### 16.3. Доступность

Все кнопки имеют понятные доступные имена; иконки не заменяют подписи важного действия. Canvas имеет текстовое описание, а журнал и числовой ввод предоставляют эквивалентный доступ к данным и направлениям.

Фокус остаётся внутри открытого modal-sheet и возвращается на исходную кнопку. `aria-live` сообщает о сохранении отметки и ошибке, но не озвучивает каждую десятую секунды таймера. Уменьшенная анимация поддерживается. Не запрещать пользовательское масштабирование всей страницы через `user-scalable=no`.

## 18. Порядок реализации и критерий готовности

Подробный backlog — `IMPLEMENTATION.md`.

**Этап 1:** извлечь чистые расчёты, описать v3 и миграционные fixtures. **Этап 2:** выполнить один полный офлайн-промер в React. **Этап 3:** журнал, цели, восстановление и переносимость. **Этап 4:** станции, снимок и датчики. **Этап 5:** 3D-наблюдения, PWA update/offline, нагрузочные и физические тесты.

Каждый этап заканчивается работающим вертикальным сценарием, а не набором пустых компонентов. Не оставлять карту макетом до самого конца и не начинать с красивой 3D-поверхности.

**Definition of Done:** пройдены применимые сценарии раздела 17; исходные данные v1/v2 доступны после миграции; повторный офлайн-запуск проверен; нет автоматического обновления посреди промера; адаптеры освобождают ресурсы; нет выдачи оценок за измерения; опубликована production-сборка либо явно указано, что публикация не выполнена. «Готово на телефоне» допустимо только после теста физического устройства.

## 19. Решения, которые не надо заново обсуждать при старте

Рабочий вариант — React web/PWA, без backend и без регистрации. Главный экран — сектор с контекстным нижним управлением. Справка отдельно. Источник истины — обороты и наблюдения; глубина не вычисляется из секунд. Снимок и датчики необязательны. Визуальную основу брать из HTML. Кандидаты допускаются внутри луча. Данные v1/v2 должны переноситься.

Нужны проверки в ходе реализации, а не новый общий дизайн-бриф: CORS и capabilities выбранного WMS; сенсоры на целевых телефонах; фактический performance budget; корректность offline на выбранном HTTPS-хостинге.
