# Supabase для Маркера

Полевой промер и локальный журнал работают без Supabase. Для подключённого проекта миграция и Edge Function `marker-login` развёрнуты 26 сентября 2026 года. Реальный вход и RLS проверены двумя временными профилями: собственные сессия и заброс создаются, читаются и обновляются; второй профиль их не видит и не может изменить. Проверочные записи и профили удалены. Для другого проекта выполните шаги ниже.

1. Создайте проект Supabase. Примените [миграцию](migrations/20260926094535_survey_cloud.sql) через `supabase db push` после `supabase link`. Она создаёт таблицы с ревизиями и RLS для сохранённых рыбалок и забросов. Политики требуют совпадения владельца и серверного claim `app_metadata.marker_username`; обычный пользователь Supabase Auth без него не получает доступ к этим таблицам.
2. В **Supabase → Edge Functions → Secrets** задайте `MARKER_MVP_PASSWORD` (общий пароль группы) и отдельный случайный `MARKER_ACCOUNT_KEY` длиной не менее 32 символов. Для передачи в Supabase их можно временно хранить в локальном игнорируемом `.env.local` без префикса `VITE_`; не коммитьте файл и не добавляйте секреты в GitHub Variables, workflow или браузерную сборку. Стандартные `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` предоставляет среда Edge Functions.
3. Разверните [функцию входа](functions/marker-login/index.ts): `supabase functions deploy marker-login --no-verify-jwt`. Её конфигурация также указана в [config.toml](config.toml). Функция принимает имя пользователя и общий пароль, при первом входе создаёт подтверждённый профиль через административный API с `app_metadata.marker_username` и выдаёт сессию Supabase Auth. Клиент не может выдать себе этот claim через `user_metadata`.
4. Для браузерной сборки нужны только два публичных значения из [примера env](../.env.example): URL проекта и publishable key. Для GitHub Pages задайте те же имена как **repository Variables**. Пароль и `MARKER_ACCOUNT_KEY` не имеют префикса `VITE_` и не попадают в браузер.
5. Проверьте реальный проект: войдите под двумя разными именами, сохраните и синхронизируйте запись, убедитесь, что другой профиль её не видит; выйдите и войдите снова. Локальный RLS-тест в `tests/rls.sql` не заменяет эту проверку. Черновики и импортированные карты остаются на устройстве.

Один общий пароль даёт доступ к **любому имени пользователя**. Это профили доверенной небольшой группы, не персональная защита данных от участников группы. Для открытой регистрации нужны индивидуальные секреты или другой способ входа. Используйте длинный случайный общий пароль и не публикуйте его. `MARKER_ACCOUNT_KEY` связывает имя с внутренним Auth-профилем: после создания пользователей менять его без миграции их учётных записей нельзя. Смена общего пароля останавливает новые входы со старым паролем, но **не отзывает уже выданные сессии Supabase Auth**; при необходимости отзыва их надо завершить отдельно.

При записи клиент отправляет сессию до её забросов. `expectedRevision: 0` создаёт запись; последующие изменения используют последнюю подтверждённую ревизию. Конфликт требует выбора версии, а не молчаливой перезаписи. `service_role` используется только внутри Edge Function для создания Auth-профиля; обычные данные защищены RLS.
